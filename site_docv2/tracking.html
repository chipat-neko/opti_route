Lien tracking destinataire

Une URL de 20 caractères, plusieurs façons d'y arriver.

Certains logiciels métier de gros clients industriels imposent une URL de tracking limitée à 20 caractères maximum. Voici quatre stratégies techniques pour répondre à cette contrainte, avec leurs implications opérationnelles.

Le calcul d'une URL de 20 caractères

Pour rentrer dans la contrainte stricte d'un logiciel client, chaque caractère compte. Le format complet de l'URL est contraint comme suit.

Décomposition d'une URL conforme

Exemple : https://fa28.ro/abcd = 20 caractères pile.

  • https:// = 8 caractères, obligatoire pour la sécurité
  • fa28.ro = 7 caractères, domaine court (5 € par an)
  • / = 1 caractère, séparateur
  • abcd = 4 caractères, code unique généré aléatoirement (1,6 million de combinaisons possibles)

Avec un domaine en .fr (3 caractères de TLD au lieu de 2), il faudrait raccourcir le code à 3 caractères, ce qui reste suffisant pour 46 656 combinaisons mais offre moins de marge.

Pourquoi les TMS du marché ne suffisent pas seuls

La plupart des TMS (Transport Management Systems) modernes proposent déjà un suivi destinataire natif : portail web, notifications push, email, SMS. Mais leur URL native est généralement bien trop longue pour respecter une contrainte stricte côté client.

Format URL TMS typique

La plupart des TMS génèrent une URL du type portail.tms.com/track/[id-long-uuid-securise], ce qui peut atteindre 60 à 100 caractères selon le format d'identifiant utilisé.

Pourquoi un format aussi long ?

Les TMS visent des destinataires qui reçoivent l'URL par email ou SMS personnel. La longueur n'est pas une contrainte dans ces canaux. Le format identifie de manière unique et sécurisée chaque envoi.

Le besoin spécifique 20 caractères

Quand le destinataire est un logiciel B2B (gestion de stock chez un grand industriel par exemple), le champ peut être contraint pour des raisons d'affichage tableau, d'export CSV ou de compatibilité legacy.

Quatre stratégies techniques possibles

Chaque option présente un compromis différent entre rapidité de déploiement, autonomie et qualité d'intégration avec l'existant. Le choix dépend du contexte opérationnel.

Disponible immédiatement

Option A — Standalone autonome

Le lien et la page tracking sont entièrement gérés côté opti_route. Le statut de livraison et la photo preuve sont poussés depuis l'application mobile au moment où le chauffeur valide la livraison.

  • Domaine court (5 €/an) + hébergement Cloudflare Workers gratuit
  • Source de vérité : application opti_route
  • UX 100 % contrôlée, design adapté à l'image souhaitée
  • Déployable en 1 à 2 jours

Limite : si l'agence utilise aussi un TMS interne, le chauffeur saisit la livraison deux fois (une fois dans le TMS, une fois dans opti_route). À considérer selon le workflow réel.

Sous condition partenaire

Option B — Redirection vers TMS

Le domaine court fait une simple redirection HTTP vers l'URL tracking native du TMS partenaire. Le TMS reste la source de vérité unique, opti_route ne fait que raccourcir le lien.

  • Domaine court seul (5 €/an), aucun coût supplémentaire
  • Source de vérité : TMS partenaire (zéro double saisie)
  • UX subie : le destinataire voit la page du TMS
  • Déployable en quelques heures si l'URL TMS est connue

Condition : nécessite que le TMS expose des URLs publiques avec un format prédictible (slug d'identifiant accessible côté backend). À valider avec le DSI partenaire.

Partenariat formel

Option C — Couplage API

La page tracking est hébergée côté opti_route, mais alimentée par appel API vers le TMS partenaire à chaque consultation. La donnée vient du TMS, l'affichage est custom. Combinaison la plus aboutie.

  • Domaine court (5 €/an) + Worker serverless gratuit
  • Source de vérité : TMS partenaire (intégrité garantie)
  • UX 100 % contrôlée, adaptée à l'image client final
  • Délai 2 à 4 semaines (accord partenaire + développement + tests)

Condition : nécessite un accès API partenaire formalisé (clé d'API, conditions d'usage, SLA minimum). Souvent lié à un accord commercial.

Déploiement à l'échelle

Option D — Hybride dual

Combine les options A et C : standalone pour les agences sans TMS, couplage API pour celles qui l'ont. Une seule interface destinataire quel que soit le contexte opérationnel de l'agence.

  • Routage interne automatique selon l'agence
  • Couverture 100 % des cas terrain
  • Double effort de développement et de maintenance
  • Justifié seulement à partir d'un certain volume

Recommandé : pertinent uniquement après validation d'un déploiement multi-agences (plus de 5 agences actives sur la solution).

Recommandation par étape

Une stratégie en trois temps qui maximise la valeur immédiate tout en gardant la porte ouverte aux meilleures intégrations.

Court terme — Option A

Déployer immédiatement le standalone autonome. Permet une démo concrète sous quelques jours, un retour terrain rapide et une preuve de concept tangible auprès du client final contraint.

Décision attendue : validation du domaine court (choix entre marque générique et marque sectorielle).

→ Voir la maquette de suivi destinataire (démo)

Moyen terme — Option B ou C

Lors de la première rencontre avec l'équipe technique du TMS partenaire, demander : « expose-t-il une URL publique stable pour le tracking ? ». Si oui, basculer en Option B. Sinon, négocier un accès API pour Option C.

Bénéfice : élimination de la double saisie, source de vérité unique côté TMS, conformité maximale.

Long terme — Option D si pertinent

Si le déploiement se généralise à plusieurs agences avec des contextes mixtes (certaines sur TMS, d'autres non), l'Option D permet une expérience unifiée côté destinataire quel que soit le contexte opérationnel.

Seuil de rentabilité : environ cinq agences actives avec contextes différents.

Position commerciale vis-à-vis du TMS partenaire

Cette intégration n'est pas en concurrence avec le TMS existant. Elle est complémentaire et résout un cas d'usage spécifique non couvert nativement.

Argumentaire d'ouverture

Le besoin client est précis : une URL de tracking strictement limitée à 20 caractères pour rentrer dans un logiciel métier gros donneur d'ordre. Le TMS partenaire gère parfaitement le tracking destinataire en standard, mais son format URL natif dépasse cette contrainte.

Deux options non-conflictuelles sont possibles :

  • Soit le TMS expose une URL publique stable, opti_route fait juste un raccourcissement et un branding adapté
  • Soit le TMS expose une API, opti_route construit une page custom alimentée par cette API

Dans les deux cas, le TMS garde la source de vérité. opti_route ne fait qu'adapter le format de présentation à une contrainte spécifique d'un client final. C'est un service de packaging, pas de remplacement.

L'option standalone est prête à être déployée

Le scaffold technique côté application mobile et page web est déjà codé. Il manque l'achat du domaine court et l'ouverture du compte Cloudflare pour la mise en service.
