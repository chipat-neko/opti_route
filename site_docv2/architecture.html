Architecture technique

Une stack moderne, scalable et conforme RGPD.

L'architecture est volontairement scindée en trois couches indépendantes : application mobile autonome, dashboard web statique sans serveur, services tiers activés à la demande. Chaque couche peut évoluer sans casser les autres.

Couche 1 — Application mobile

Le cœur fonctionnel. Tout est embarqué sur le téléphone du chauffeur-livreur. L'application reste pleinement opérationnelle sans réseau.

01 Mobile cross-platform Flutter

Stack Flutter pour produire une seule base de code utilisable sur Android (Phase 1) puis iOS (Phase 3). Compilation native pour des performances proches du natif pur. UI fluide même sur les téléphones d'entrée de gamme.

Couche 2 — Dashboard web companion

Outil web léger pour visualiser les exports CSV de l'application, utile pour un chef d'équipe ou une direction qui veut un tableau de bord sans manipuler l'application mobile.

03 Web statique, sans serveur

HTML, CSS et JavaScript vanilla, hébergés sur GitHub Pages. Aucun backend, aucune base de données serveur, aucun cookie. Le CSV est parsé en mémoire dans le navigateur, rien n'est uploadé. Zéro coût d'hébergement, zéro risque de fuite de données par le canal web.

Couche 3 — Services tiers à la demande

Activés uniquement quand les fonctionnalités correspondantes sont demandées (Phase 2 cloud collaboratif, Phase 3 intégrations). Hébergement Europe systématique pour conformité RGPD.

04 Backend cloud collaboratif

Supabase comme socle Phase 2 : PostgreSQL géré, authentification, Realtime websockets, Storage objet pour les photos preuves. Région EU-West pour conformité RGPD. Sécurité par Row-Level Security au niveau base, isolation des données par utilisateur ou par équipe.

Garanties intégrées dans l'architecture

Trois engagements structurels qui sécurisent l'utilisation à long terme.

Conformité RGPD by design

Phase 1 : aucune donnée ne quitte le téléphone, donc aucun transfert hors UE possible. Phase 2 et 3 : hébergement systématique en région EU-West, chiffrement au repos, accès par utilisateur via Row-Level Security.

Indépendance fournisseur

Les composants critiques sont open source (Flutter, VROOM, OpenStreetMap, SQLite). Le code applicatif est sous contrôle versionné public. En cas de défaillance d'un service tiers, un remplacement reste possible sans réécrire l'application.

Couverture par tests automatisés

834 tests automatisés couvrent les fonctions critiques (optimisation, géocodage, parsing OCR, sécurité PIN, sauvegardes). Chaque modification du code passe par cette batterie avant publication, garantissant la non-régression.

Mises à jour mensuelles

Cycle de publication mensuel typique, avec patches correctifs intermédiaires si bug critique. Distribution Android par APK GitHub Releases (Phase 1 et 2), Play Store envisageable en Phase 3 quand la fréquence de mise à jour diminuera.

Migrations de base de données versionnées

Le schéma SQLite local évolue par migrations explicites (v1 à v36 à ce jour). Aucune perte de données entre versions, rollback possible via sauvegarde ZIP. Le mécanisme est également appliqué côté cloud Postgres.

Documentation maintenue

Documentation produit (ce site), documentation utilisateur (FAQ, guides), documentation développeur (CLAUDE.md interne, commentaires en français dans le code). Chaque PR enrichit la documentation correspondante.

Décisions d'architecture clés

Cinq choix structurants qui expliquent pourquoi le produit est robuste, scalable et indépendant.

Pourquoi Flutter ?

Une seule base de code pour Android et iOS, avec performances proches du natif. Permet d'éviter de doubler les coûts de développement entre les deux plateformes en Phase 3.

Pourquoi SQLite local d'abord ?

Aucune dépendance réseau en Phase 1, fonctionnement parfait en zone blanche (zones rurales, sous-sols, parking souterrains). Le cloud arrive en Phase 2 en complément, jamais en remplacement.

Pourquoi Supabase plutôt que Firebase ?

Supabase est entièrement open source et propose un hébergement Europe. Firebase est lié à Google et basé aux États-Unis, ce qui pose problème pour les données clients européens. PostgreSQL standard, donc migration possible si besoin.

Pourquoi Cloudflare Workers pour le tracking ?

Latence sub-100 ms partout dans le monde, free tier généreux (100 000 vues par jour), support natif des domaines personnalisés. Idéal pour servir une page tracking légère en haute disponibilité sans coût récurrent significatif.

Pourquoi GitHub Pages pour le site ?

Hébergement statique gratuit à vie, CDN mondial inclus, déploiement automatique au push. Pas de risque de panne serveur sur la page publique, pas de coût d'opération.

Pourquoi le mode hors-ligne natif ?

Le métier de chauffeur-livreur implique des zones réseau faible ou nul (sous-sol, ascenseur, campagne). Sans mode hors-ligne robuste, l'outil deviendrait inutilisable plusieurs fois par jour. C'est un prérequis non négociable.
